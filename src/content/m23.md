Interface management transforma dependências implícitas em compromissos verificáveis: **quem fornece qual dado, em que revisão, quando, com qual critério de aceite e qual documento absorve a decisão**.

**Pré-requisitos:** Nenhum. Este capítulo é útil desde o primeiro dia de qualquer projeto multidisciplinar.

### O problema que você realmente está gerenciando

Em um projeto submarino, quase nenhum equipamento “fecha sozinho”. Uma árvore depende de wellhead, tooling, controls, hubs e linhas; um riser depende de end fitting, bend stiffener, host structure, pull-in system, vessel e análise global; um umbilical depende de UTA/SDU, SCMs, topside control/power e flying leads. O risco nasce quando duas partes avançam com **versões diferentes da mesma interface**.



| Objeto de gestão | Pergunta que fecha a interface | Evidência |
|---|---|---|
| Requirement | O que precisa ser verdadeiro? | Spec/contract/design basis + requirement ID. |
| Input data | Quem entrega qual dado e até quando? | Interface register / document schedule / TQ. |
| Geometry | Datum, envelope, tolerance e orientation são comuns? | Interface drawing / 3D model / clash review. |
| Loads | Quem calcula, quem recebe e quem aprova? | Load report + structural check + revision alignment. |
| Control/data | Protocol, I/O, software e configuration estão alinhados? | ICD, I/O list, software baseline, SIT. |
| Test/acceptance | Onde a interface é comprovada? | FAT/EFAT/SIT/SAT + acceptance record. |

#### VDRL, MDR e vendor data sem burocracia inútil

**VDRL** (Vendor Document Requirement List) é uma obrigação de entrega; **MDR** (Master Document Register) é o mapa de documentos/configuração do projeto. O valor deles não está em contar PDFs. Está em saber quais documentos **liberam fabricação, procurement, integration test, mobilization e offshore execution**. Um documento “90% pronto” pode ser inútil se ainda contém exatamente o TBD que outra empresa precisa para fabricar.

#### Fluxo de mudança

Uma boa mudança técnica passa por: origem → impacto → decisão → atualização de interface/documentos → comunicação → verificação. Se a decisão morreu no e-mail ou na ata e não entrou no desenho, calculation note, BOM, software/configuration ou procedure afetado, a mudança ainda não está fechada.

## Painel PM

### Pontos de atenção

- Controle interfaces por conteúdo e maturidade, não apenas por status “open/closed”.
- Associe documentos críticos a marcos físicos: procurement, fabrication, FAT, mobilization, offshore.
- Trate TQ/RFI como fluxo de decisão com prazo e impacto, não como caixa de e-mail.

### Perguntas que você deve fazer

- Qual interface ainda usa dado preliminary/TBD?
- Qual fornecedor está esperando input de outro e em qual data isso vira critical path?
- Onde esta decisão será incorporada na configuração?
- Qual teste prova que a interface fechou no sistema real?

### Documentos que valem abrir

- Interface Register / ICD / Interface Drawing
- VDRL / MDR / document schedule
- TQ/RFI log, decision log e change/MOC register

## Red flags

- Interface “fechada” sem documento/configuração revisada.
- Dois fornecedores referenciando revisões incompatíveis.
- Documento crítico atrasado, mas cronograma físico não mostra impacto.

### Pergunta 1 (id: m23-0)

**Enunciado:** Uma interface pode ser considerada fechada quando:

- [ ] Foi discutida em reunião
- [x] A decisão está incorporada nos documentos/configuração aplicáveis e existe evidência de verificação
- [ ] O prazo passou

**Feedback (resposta correta):** Interface fecha quando dado, owner, configuração e evidência estão alinhados.

### Pergunta 2 (id: m23-1)

**Enunciado:** Qual uso é mais maduro do MDR/VDRL?

- [x] Relacionar documentos a inputs, gates e deliverables físicos
- [ ] Contar quantos PDFs chegaram

**Feedback (resposta correta):** VDRL/MDR têm valor quando conectados a decisões e gates físicos.

### Pergunta 3 (id: m23-pm)

**Enunciado:** Cenário de PM: dois fornecedores usam interface drawings de revisões diferentes. O que você faz?

- [ ] Mantém ambos e resolve no SAT
- [x] Congela a interface, identifica revisão governante/impactos, emite decisão controlada e verifica atualização
- [ ] Escolhe a revisão mais recente pelo nome do arquivo

**Feedback (resposta correta):** O primeiro passo é tornar a divergência explícita e impedir que fabricação avance sobre bases diferentes.
